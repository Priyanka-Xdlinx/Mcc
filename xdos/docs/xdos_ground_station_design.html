01 Introduction

What this system is, and what this document covers

The XDOS ground station is the Level-1/Level-2 ground software for the XDOS satellite. It gives an operator a single console from which every subsystem can be commanded, models the spacecraft closely enough that the whole command-and-telemetry path can be exercised on a desk, and decodes the housekeeping telemetry the on-board computer sends down on its own schedule.

Scope

This document records what has been built, how the pieces fit together, and what the wire contracts are. It is written for an internal technical review: it assumes familiarity with spacecraft telecommanding but not with this codebase, and every figure in it is quoted from the working tree rather than from a plan. It covers the process architecture and network interfaces, the layered structure of the codebase, the telecommand path end to end, the CCSDS frame formats, the binary rate-group look-up table, the simulation environment and power model, and the verification status.

Out of scope: the radio-frequency layer, the flight software running on the real on-board computer, and the spacecraft platform itself. Where this document refers to the on-board computer, it means the bench model implemented in this repository, which presents the same interfaces as the flight article.

02 System overview

Five processes, one host, every link a plain TCP socket

An operator works in the telecommanding CLI; that CLI talks to the on-board computer, which routes each command to the subsystem that owns it. In parallel, and without being asked, the on-board computer polls a set of housekeeping telecommands on a fixed cadence and pushes the results to a separate telemetry terminal.

Because every link carries the real wire format over an ordinary socket, any node in the diagram can be replaced by hardware without changing the software on either side of it. Substituting the real on-board computer for the bench model is a matter of pointing the CLI at a different address and port.

Three characteristics of the layout are worth drawing out before the detail:

  • Side channels are physically separate. Pushed telemetry, EGSE power status and look-up-table uplinks each get their own port.
  • Routing is by identity, not by content. The bridge selects a subsystem from the APID inside the CCSDS frame; it never parses the subsystem payload.
  • The on-board computer is database-free. It carries no command definitions at all. What it polls, and which response bytes it keeps, are uplinked to it as an opaque binary table.

Network interfaces and port allocation

Ports are allocated relative to a single routing port, written P. It is 10000 in simulation and 7000 on the bench; the three side channels always sit at P+1, P+2 and P+3, so moving between environments changes one number.

03 Software architecture

One static library carries every layer; the executables are thin shells over it

Dependencies point downward only. Third-party code is limited to a vendored nlohmann/json header and Catch2 v3 for the test target; everything else is C++17 standard library plus the platform socket API, which keeps the Windows port to a single compatibility header.

Data-driven by design

Almost nothing about a subsystem is compiled in. Command listings, field offsets and sizes, enumerations, units, PDU channel labels and the CCSDS frame layout are all read from JSON at start-up, so a database revision changes behaviour without a rebuild — and the same profile drives encoding and decoding, so the two directions cannot disagree.

  • mib/*.json — one file per subsystem: every telecommand and telemetry message with its parameters, offsets, sizes, types, units and enumerations. 418 messages in total.
  • mib/ccsds_tc.json, mib/ccsds_tm.json — the frame profiles: spacecraft identity, APID map, field layout, rate-group APID.
  • config/flight.json — the power sequence: boot time, stagger, switch-on order, battery thresholds, load-shed sets, orbit period.
  • config/rate_group_commands.csv — the master list of housekeeping commands from which the binary LUT is compiled.

04 Telecommand path

Ten steps from an operator keystroke to a decoded, unit-tagged response

Resolving what the operator typed

Identifier resolution is deliberately forgiving but never ambiguous. It tries, in order, an exact specification-ID match with alphanumeric normalisation (so ep19 resolves EP-019), then a numeric-tail match, and finally a plain numeric message identifier. Where a numeric tail could match more than one specification ID, the resolver lists the collisions instead of guessing.

Operator main menu
KeyAction
1 / 2 / 3Send a telecommand to ADCS / EPS / GPS
4 / 5 / 6Send a telecommand to Payload / XLINK-S / UHF
pPower control — kill switch, per-subsystem ON/OFF, orbit state
gBinary rate-group LUT: CSV import, pick editor, build and uplink
cToggle CCSDS framing on the flight link
! / h / r / qRepeat a recent command / help / reconnect the buses / quit

Within a listing, Enter pages forward, b steps back one level and q quits. ADCS offers a kind filter first — set, get, act or all — because its listing runs to over 150 entries.

05 CCSDS framing

The Level-2 wire contract, drawn to scale

Both frame layouts are loaded from JSON profiles rather than compiled in, and the telemetry profile references the telecommand profile, so spacecraft identity and the APID map are shared between the two directions.

Telecommand frame

  • Version, bypass and control-command flags, spacecraft ID 625 and virtual-channel ID live in the transfer-frame header; the inner space-packet header carries the subsystem APID.
  • Time code on the uplink is the 8-bit-centisecond CCS variant.
  • TC-ID mirrors the subsystem command identifier, so a reply can be matched to its command without keeping state.

Telemetry frame

  • The master-frame and sub-frame counters in the primary header give the ground its slot: SFC mod 16 is the subframe index, SFC div 16 the master-frame identifier.
  • Time code on the downlink is the 16-bit-millisecond variant — the one deliberate difference between the two secondary headers.
  • A lost frame therefore leaves a visible gap rather than shifting every later subframe out of alignment.

06 Rate-group telemetry and the binary LUT

The flight computer polls and downlinks housekeeping without knowing what any of it means

Why it exists

Housekeeping telemetry has to be polled continuously and downlinked on a fixed cadence. The obvious way to do that — teach the flight computer the subsystem databases — was rejected for three reasons. It would mean carrying a parser for six different protocols on board. It would mean re-flashing the on-board computer every time a subsystem database was revised. And it would not, by itself, solve the real constraint: the downlink budget is fixed and small, so what is sent has to be selected byte by byte.

The design adopted instead puts one binary file on board that tells the on-board computer three things: which telecommands to replay, which bytes of each response to keep, and where those bytes go in the downlink block. There are no names and no identifiers anywhere in the file; all meaning stays on the ground, in the database and in a JSON twin that is never transmitted.

What the design buys

  • No on-board database. The OBC boots with no table and transmits nothing until one is uplinked or a stored one passes CRC — a deliberate fail-silent default.
  • Change without re-flashing. Edit the CSV, rebuild, uplink; the engine hot-swaps the running table and keeps its slot phase.
  • Deterministic and quotable. An identical table always produces a byte-identical file, so its CRC-16 signature can be cited in a review.

Where failures land

  • Unknown command or parameter names are rejected at build time.
  • Picks that fall outside the declared response length are rejected at build time.
  • A tier whose selected bytes exceed its budget is rejected at build time, with the tier and the offending entry named.
  • None of these conditions can arise at runtime.

Authoring

The intended route is a single master list, config/rate_group_commands.csv, with one row per rate-group command and five columns.

Watch the range syntax

bytes 4:2 means offset 4, size 2 — bytes 4 and 5. It is not a start-to-end range. Selections are sorted, and adjacent or overlapping ranges merge automatically, so eight flags packed into one byte cost exactly one byte.

File format

All multi-byte values are little-endian. The file is a 50-byte header followed by four segments — Very High, High, Medium and Low — of variable-length entries packed back to back.

The whole runtime job

memcpy(block + block_off, payload + src, size) — zero interpretation. Picks address the raw payload, that is the database byte space with all native framing excluded.

Subframe and master-frame layout

Every subframe carries all four tiers at fixed offsets. The tiers differ only in how many subframes a block spans, and therefore in how much unique data each block holds.

With the present 78-command classification, Very High is the tight tier at roughly 14.8 bytes of picked data per command, and it is where the generator's budget check will bite first.

On-board execution and cadence

The engine derives a sixteen-position schedule when a table is loaded: entry i of tier t is polled in the slots where the slot number modulo the tier's span equals i modulo that span. Polls are spread evenly across each one-second window with a 50 ms link-pacing floor between them. A window that overruns finishes late and is counted, but never skips a slot, so block phase is preserved.

Poll results land in per-tier block buffers of 400, 800, 1200 and 1400 bytes. A failed poll writes 0xFF over that entry's pick ranges — the ground's subsystem-down marker — and block bytes that no pick claims stay zero.

07 Simulation environment and flight power model

The simulators answer from live models, so the ground station meets values that change

Physics-backed engines

  • EPS. State of charge and battery voltage propagate against the orbit — 3300 s sunlit, 2100 s eclipse — with the PDU channel mask setting the load.
  • ADCS. An attitude quaternion propagates under a PD controller; set, get and act commands move the modelled body and the telemetry follows.
  • GPS. A Keplerian propagator sits behind the native message set, so LOG commands return position, velocity and time as the receiver would.

Protocol-level responders

  • Payload, XLINK-S and UHF return structurally correct replies — acknowledgement bytes, keyed S-band events and OpenLST transceiver responses — without modelling physics.
  • They are enough to exercise framing, routing and the operator flows end to end.

Power finite-state machine

The on-board computer's power behaviour runs UNPOWERED → BOOTING → SEQUENCING → ON, returning to UNPOWERED whenever the kill switch is turned off. While the machine is not ON the bridge drops every frame from the ground, with one exception: EGSE umbilical frames are always answered, so the ground can see the power state at any point during boot.

Battery thresholds and load shedding
Battery modeThresholdChannels shed
Full≥ 12.0 VNone
Normal≥ 11.1 VNone — the default switch-on sequence is restored, staggered and rate-limited
Safe≥ 9.9 VPayload (O10)
Critical≥ 9.0 VPayload, ADCS and the avionics bus (O10, O4, O3)
Below critical< 9.0 VEverything except the two on-board-computer channels (O1, O2)

A hysteresis of 0.15 V keeps a battery sitting on a threshold from oscillating between modes. All timing honours a time-scale factor, so a boot-and-sequence run that takes real seconds on the bench compresses into milliseconds under test.

09 Build, run and operations

Two commands to build, one script to bring the stack up

From the repository root: cmake -B build -DCMAKE_BUILD_TYPE=Release then cmake --build build -j. The test target is built when Catch2 v3 is available; a Windows build is described in BUILD_WINDOWS.md.

Operating notes

  • Launch the operator CLI from the repository root so config/ and mib/ are visible; the LUT composer reads and writes files there.
  • The on-board computer transmits no telemetry at all until a binary LUT has been uplinked, or a stored one has passed its CRC check at boot. Silence on the telemetry port is the expected state before the first uplink, not a fault.
  • Rate-group telemetry is displayed by the standalone viewer, not by the operator CLI. The CLI keeps the LUT uplink flow, because that is telecommanding.
  • Passing the no-colour flag strips the ANSI escapes, which makes output suitable for piping to a file.

10 Status and proposed next steps

The frame layout is final and the LUT path is implemented end to end

Delivered and verified

  • Telecommanding of all six subsystems, MIB-driven, over CCSDS telecommand frames.
  • CCSDS telemetry downlink in the fixed 1432-byte frame, decoded and rendered on the ground.
  • The full binary LUT path: CSV compilation, uplink, independent on-board verification, hot-swap and persistence across restarts.
  • Tier-scheduled polling with a sixteen-position schedule and slot-aligned master frames.
  • A flight-realistic power sequence with load shedding, hysteresis and staggered restore.

Proposed next steps — for review

  • Exercise the bench port map — the 7000 series — against the real on-board computer, including the LUT listener on port 7003.
  • Bring Payload, XLINK-S and UHF commands into the rate-group classification; the present 78-command list is dominated by ADCS, EPS and GPS.
  • Watch the Very High tier as the classification grows.
  • Extend structured validation reporting to the operator CLI's downlink path.
  • Housekeeping: refresh README.md, which still describes CCSDS wrapping as deferred although it is implemented, and retire src/cli/main.cpp.old.

Decisions closed
