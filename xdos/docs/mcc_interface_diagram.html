MCC Subframe Feed

How rate-group telemetry travels from the spacecraft bus to the MCC software, and what arrives on the MCC TCP socket.

  • protocol XMCC v1
  • header 26 B
  • payload 1280 B
  • message 1306 B
  • cadence 1 Hz

End-to-end path

Four hops. The OBC polls the bus and pushes one subframe per second; the ground station positions it in its master frame, decodes it for the operator, and forwards the payload on to MCC.

What MCC receives

One TCP message per subframe: a fixed 26-byte header saying where and when the subframe belongs, then the payload. All header fields are big-endian.

The timestamp is spacecraft time, passed through untouched

It is the subframe's own CCS Time Code, copied field for field out of the TM header — not a ground receive time, and deliberately not converted to a Unix epoch, so no timezone or leap-second handling sits between the spacecraft and MCC.

Inside the payload

The 1280 bytes are partitioned into four priority tiers at fixed offsets. Only VH is complete in a single subframe — the others are slices of a wider block.

All 0xFF means "no answer"

The OBC pre-fills every picked byte range with 0xFF and rewrites it with 0xFF when a poll fails. It is a down marker, never a reading of 255.

0x00 is unclaimed space

Bytes no parameter picks are zero-padded. Both markers matter when deciding whether a field is stale.

Names come from the ground twin

The payload carries no names and no identifiers — only bytes at known offsets. Position within a tier is the only link between what the OBC sends and what the ground decodes, so MCC needs rate_group_lut_bin_gs.json to name anything, and must confirm its CRC-16 matches the table the OBC is running. Decoding against a mismatched twin reads every value from the wrong offset and still looks plausible.

The table being flown

Discard the first master frame

From a cold start the blocks begin at 0xFF and each entry is polled only when its turn comes round. Measured: VH is complete from subframe 1, H from 4, M from 11, and L does not fully populate inside the first master frame at all. Everything reads valid from the second master frame onward.

Recent changes

  • LUT rebuilt from the pick sheet — 12 entries grew to 64 across EPS, ADCS, GPS, UHF and XLINK-S; 833 highlighted parameters resolved to database names. Binary is 2118 B, CRC-16 0xAFEE.
  • Poll pacing is derived, not fixed — the gap between polls is T_sf / entries (33 polls in a 1000 ms window → 30 ms), replacing a fixed 50 ms per command that demanded 1650 ms of a 1000 ms window. Measured cadence holds at 1.000 s with zero overruns.
  • Tier coverage debug — every subframe now reports all four tiers, so H, M and L are visible on the subframes where their block has not closed yet, instead of only when it completes.
  • MCC forwarding — this interface, in either socket direction, now carrying the subframe timestamp.

Connecting

The link is one-way; the ground station only sends. Either side may own the socket:

ModeGround stationMCC softwareGS launched with
ATCP serverTCP client--mcc-listen [HOST:]PORT
BTCP clientTCP server--mcc-connect HOST:PORT

No handshake, no login, no keep-alive — data starts on the next subframe after the socket is up. Mode A fans out to every connected client and drops one that stops reading; mode B retries on the next subframe after a failure. Anything MCC sends on this socket is ignored.
